## 隔离宿主与打包

所有宿主探针在临时项目、独立注册表、独立配置及本机回环服务中执行；脚本化模型只在本机运行，不访问外部模型服务。

本轮重跑了强行插回 shell 的旧请求、软暂停与显式恢复、同进程专家接续、真实节点进程重启。另扩展执行探针核对 `resume:true` 同 ID 重发和重启后 seq 持续递增；输出摘要存于 review-verification.json。完整宿主配置热更新卸载顺序及所有多进程交错仍未覆盖。

- [宿主身份与消息 ID](host-probe.json)：OpenCode 2.2.5、插件 SDK 2.0.18；同 ID 重复提交获得同一 inbox 条目，同进程的两次插件 setup 保持相同进程身份。`resume:false` 的排队消息没有出现在 context，因此不能以 context 缺消息证明未发送。
- [执行事件](execution-probe.json)：验证首轮及后续轮的 inbox ID、事件顺序和终态关联；真实宿主首轮的 started 事件未被该订阅看到，因而实现允许从已交付的授权消息建立首轮关联。
- [主协调权限](coordinator-boundary-probe.json)：普通会话的 shell 测试副作用成功；主协调没有该副作用。测试插件强行把 shell 放回主协调的旧请求后，执行前检查仍拒绝了它。
- [研究派发与软暂停](research-run-probe.json)：真实宿主依次完成 propose、dispatch、节点 finish；暂停期间节点完成，启动预留数在暂停前后保持 3。不同路径别名曾使宿主建立两个 attachment，现由当前控制器接收旧 attachment 的调用。
- [独立打包验证](packed-probe.json)：`scripts/probe_packed_release.py` 通过实际 prepack 创建并解包 tarball，删除临时构建树后确认 Python 后端来自解压包；依赖解析使用本机已安装的固定 SDK。正常派发、暂停／恢复和只读专家交付均通过；专家执行中 stop 得到原生 interrupted 终态，节点执行仍保留未核实。解包后端还通过 `plugin/test/package.test.ts` 的迁移、结项和重启测试。
- 对解包后的**临时测试副本**注入两种故障：节点 kickoff 已被宿主接受但返回值丢失，以及报告已被宿主接受但返回值丢失。前者停在一个未核实节点，原生轮次结束后没有自动续轮；用户核实退出并显式恢复／重试后才产生第二个、不同 ID 的启动。后者显示待核对通知，核实宿主消息后保留原 ID 并确认交付。注入只用于探针，不在产品代码里增加故障开关。
- 真实宿主进程在节点或专家运行中被强制结束并重启后，项目暂停，原节点及在途专家保持未核实；显式 resume 后未重新启动。另由测试插件在活跃专家期间调用修复插件的 setup，模拟同进程重绑定：进程身份不变、fence 前进、项目保持运行，专家按原身份、工具范围和期限完成，只有一个专家启动。该演练使用真实宿主上下文，但不是宿主配置文件热更新的卸载流程。

## 历史记录迁移

`scripts/probe_legacy_migration.py` 从一个没有未落盘 WAL 的历史测试项目只读建立临时数据库副本。先用 PR #8 的代码把 schema 9 升到 11，再用本分支升到 12；对照 11→12 前后的 62 张历史表，原有列的逻辑内容全部一致，包含 67 个 event 和 64 个 request。schema 11 备份与升级后的数据库均通过 integrity check。原项目早于持久预算，因此在副本中添加了一条合成预算记录来检查其保留；CAS 行为和历史成功请求重放另由自动测试覆盖。原项目在复制期间的大小和修改时间未改变。
