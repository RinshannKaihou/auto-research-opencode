# auto-research-opencode · 自主研究插件（OpenCode V2）

版本 v0.1.1（实验版本）。安装、更新、卸载和常见问题见[仓库根目录的 README](../README.md)；这份文档讲插件怎么工作。

这是面向 OpenCode V2（`@opencode/plugin` 2.0.18）的研究插件。**它以自主推进为底层**：你给出研究目标后，插件驱动模型自己完成规划、派发、执行、综合和收尾。你可以随时插话指导，也可以暂停或停止。

研究账本是仓库根目录 `src/auto_research/` 下的 Python 代码，从 DSH 版 0.6.11 的 schema 9 演进到 schema 10，数据放在 `<项目>/.research/`。首次以可写存储打开项目时备份并升级 schema 9，包括研究会话的状态查询或恢复；独立只读浏览不升级。旧版不能直接写入 schema 10，回退代码不会自动降级账本。

## 结项契约

主协调发布 `status: "complete"` 的最终报告后调用：

以下字段从 v0.1.1 起全部必填，旧调用需要更新。

```json
{
  "summary": "完成受控实验，长期行为仍需研究",
  "final_ref": "pub/P-014#report",
  "outcome": "partial",
  "gaps": ["尚无长期训练证据"],
  "review": {
    "status": "unreviewed",
    "refs": [],
    "limitations": ["最终综合尚未独立审阅"]
  }
}
```

- `outcome` 为 `answered`、`partial` 或 `unresolved`；后两种必须有非空 `gaps`。空列表表示未登记未解决项。
- `review.status` 为 `unreviewed`、`partial` 或 `reviewed`；后两种必须有冻结审阅材料 `refs`，前两种必须有非空 `limitations`。三个字段均必填。它是调用者的覆盖声明，`reviewed` 不表示审阅通过。
- `final_ref` 支持整份出版物或完整条目引用。父出版物必须 `complete`，整份出版物须非空且所有条目可解析；文件对象校验完整性。`complete` 仅表示报告交付完成，允许报告未解决问题。
- 引用、契约、调用身份及存活任务检查与结项记录、主工作段结束、运行状态更新在同一事务完成。相同操作重试返回原收据；通知失败不撤销结项。不能用普通工作流状态更新跳过契约。
- 历史 pending 待审项、open 问题不会一律阻止结项。完整的科学审阅和主张覆盖检查尚未包含在此契约中。
- 状态和概览显示登记的最终引用、结果及审阅说明；后续出版物不会替换最终引用。历史 `complete` 项目无收据时显示“未记录结项契约”。重新开展研究使用 `/research auto` 创建新运行 generation。

`research_memory action=checkpoint` 默认写入当前工作对象，后端拒绝不同节点和伪造来源。恢复上下文的 `checkpoint_recovery.head_revision` 用于下一次 checkpoint 的 `expected_revision`；它可能大于显示的有效 checkpoint 版本，因为误归属历史记录被保留但隔离。来源未知的历史项目 checkpoint 不参与自动恢复。

## 一句话开始

在想放研究项目的目录里启动 OpenCode，然后在首页输入：

```text
/research auto <研究目标>
```

之后不需要再发任何消息：

1. **主协调会话**提出研究节点（`research_propose`），把节点派发出去（`research_dispatch`），然后等待（`research_wait`）。
2. 插件为每个派发的节点**新建一个执行会话**，标题形如"X-001 · 问题"，并给它一个独立的工作目录 `workspaces/branch-*/`。
3. 节点执行会话做实验，发布报告和数据（`research_publish`），记录引用这些材料的结论（`research_memory`）；需要独立复核时可以叫一位只读专家（`research_delegate`，见下文"节点内专家"）；完成或受阻时调用 `research_finish`。
4. 插件把节点结果交给主协调，唤醒它继续：综合结果，派发后续节点。
5. 目标回答后，主协调发布最终报告并调用 `research_conclude`，研究结束。

进度会显示在以下位置：
- 右侧栏研究面板；
- 输入框上方的状态条；
- 对话区的 `【Research 自动推进】…` 记录；
- `/research board` 看板。

在看板"运行"视图里选中一个会话按 Enter，就会跳到对应的节点执行会话。

## 推进引擎怎么工作

OpenCode 每结束一轮都会发出一个事件，引擎读取账本后决定下一步：

| 情况 | 处理 |
|---|---|
| 主协调这一轮有产出 | 插入一条"继续推进"消息，开始下一轮 |
| 主协调在等待，或者有节点在跑而它这一轮没有产出 | 进入等待，节点结束后再唤醒 |
| 节点调用了 `research_finish` | 结束节点工作段，把总结和发布交给主协调，调度下一个排队的节点 |
| 节点这一轮有产出但还没结束 | 让它继续 |
| 同一会话连续 3 轮没有写入任何研究记录 | 暂停这个会话（原因：没有进展） |
| 一轮出错 | 自动重试一次，再出错就暂停这个会话 |
| 你按 Esc 中断一轮 | 暂停这个会话 |
| OpenCode 重启 | 运行中的项目改为暂停，需要用 `/research resume` 继续，不会自动重跑 |

另外几条规则：
- 节点"发布了新材料"只作为消息送达主协调，不会唤醒它；只有节点完成、受阻或失败时才唤醒。
- 在研究会话里直接发的消息会被记为"用户指导"写进账本，模型照常能读到，**自动推进不会因此暂停**。
- 并行节点数默认是 1，可以用插件选项 `concurrency` 调整。
- 研究会话里没有 OpenCode 自带的 `subagent` 和 `question` 工具：后台子代理不在推进引擎的视线里，提问会让自动推进停下来等人回答。节点需要帮手时用 `research_delegate`。

## 节点内专家

节点执行会话需要另一个视角时（复核一段分析、核对结果、查阅相关材料），可以调用 `research_delegate` 叫一位**只读专家**，或者用 `research_delegate_batch` 一次叫一批同时运行。

- **怎么运行**：插件新建一个会话，标题形如"X-001 · 专家 · 标签"，发给它一张固定格式的任务单（问题、目的、材料、交付物、完成标准、回报要求）。节点的这次工具调用会一直等到专家交回报告。
- **报告去哪**：完整报告存进研究账本；节点拿到约 1600 字的预览和完整报告的文件路径，自己判断采不采用。
- **只读有两道保证**：专家会话建立时带上会话级权限规则（先全部拒绝，再放行 `read`、`glob`、`grep`、`research_query`、`research_read_input`，`.env` 文件不放行）；每次请求再按清单删掉其他工具。账本服务端也拒绝专家的一切写入。专家不能运行命令、改文件，也不能再叫别人。
- **盲评**：任务里写 `context_mode: "blind"` 时，专家只看得到分配的材料，编号为 `input-1`、`input-2`……，用 `research_read_input` 分段读取。它看不到材料来自哪份发布，看不到节点工作目录、研究记录和项目目标。OpenCode 默认塞进系统提示词的工作目录和 `AGENTS.md` 也会被替换掉。盲评材料必须是已发布的文件（`pub/P-…#item`）。
- **限制**：每个节点同时最多 2 位专家（插件选项 `specialistFanout`），一批超过上限时一个都不启动；每位专家最多 10 分钟（插件选项 `specialistTimeoutMs`），超时后收回已写的部分，记为"未完成"。
- **中断与重启**：节点这一轮被中断或 `/research stop` 时，它正在等的专家一起取消。OpenCode 重启后，还没交回报告的专家会被停下并记为"未完成"，释放名额。
- **还没有做**：DSH 版里主协调发起的项目级"整理专家"（`research_memory` 的 `consolidate`）。

## 命令

| 命令 | 作用 |
|---|---|
| `/research auto [目标]` | 目录里没有项目时，建立项目并开始（必须写目标）；已有项目时，开始或重新开始。在首页执行会自动新建或打开主会话 |
| `/research pause` | 当前这一轮做完后不再继续，节点任务保留 |
| `/research resume` | 恢复所有受插件管理的会话 |
| `/research stop` | 中断正在运行的会话，取消排队中和进行中的节点任务（需要确认），已有记录保留 |
| `/research status` | 查看项目和本会话的状态 |
| `/research board` | 打开只读看板：概览、研究过程、成果与知识、材料、运行 |
| `/research init <目标>` | 只建立项目、不开始，适合先和模型讨论方案 |
| `/research guidance [路径 [--version v]]` | 查看或登记科研指导文档 |
| `/research takeover` | 接管目录里已有的项目，包括 DSH 建的。这是**单向**操作，需要确认，而且项目必须已停止 |
| `/research detach` | 把本会话移出项目。主会话要先停止研究才能移出 |

模型能用的研究工具按角色开放：

| 角色 | 专属工具 |
|---|---|
| 主协调 | `propose`、`dispatch`、`wait`、`conclude`、`close_node` |
| 节点执行 | `finish`、`consume`、`delegate`、`delegate_batch` |
| 两者共用 | `query`、`memory`、`note`、`snapshot`、`publish`、`relate` |
| 专家 | `query`、`read_input`（盲评只有 `read_input`），外加 OpenCode 自带的 `read`、`glob`、`grep` |

## 用真实模型时的注意事项

- **审批会让推进停下**：节点执行会话要运行命令、写文件，OpenCode 默认会弹出审批，这时自动推进会停在审批上等你处理。想完全无人值守，启动时加 `--auto`（自动批准没有被明确禁止的操作），或者在配置里提前放开需要的权限。
- **请在项目根目录启动 OpenCode**：所有研究会话都放在这个目录下，由同一份插件实例管理。在子目录里打开时只能只读查看，不能控制推进。
- **同一项目不要同时在 DSH 和 OpenCode 里打开。**

## 不影响其他功能

- **没有关联研究项目的会话**：每次请求只会被去掉本插件的工具，不会加入任何上下文，也不会调用 Python；`subagent`、`question` 这些自带工具照常可用。我们在沙盒里比对过装与不装插件时的完整请求体，统一会话 ID 后完全相同。
- **Python 只在需要时启动**：已有注册表，或者第一次使用 `/research` 时才会启动。所有钩子出错时都原样放行，不影响正常请求。
- **不改全局设置**：不写全局权限规则，不改 agent 和模型；只读规则只加在插件自己建的专家会话上。界面上只增加 `/research` 命令、一个全屏页面，以及只在研究会话里出现的侧栏面板和状态条。

## 开发与测试

```bash
bun test                                           # 推进引擎、工具、角色、命令的测试（假宿主 + 真实 Python）
node_modules/.bin/tsc -p tsconfig.json --noEmit    # 类型检查
make test-python                                   # 在仓库根目录运行 Python 测试
```

改完代码后执行 `opencode service restart`，正在用的 OpenCode 才会加载新代码：插件加载在后台服务里，只重启界面不够。

端到端测试在开发沙盒里进行（不在本仓库），用按剧本应答的模拟模型，在真实的 OpenCode 2.0.18 里完整跑过一次：`/research auto` → 两个节点 → 主协调两次被唤醒 → 最终报告 → 完成。

专家另用一个剧本在真实的 OpenCode 里跑过：
- 节点 X-001 叫了一位普通专家，专家调用 `shell` 被拒绝，读研究记录后交回报告；
- 节点 X-002 用自带的 `write` 写了一份报告并发布，再交给一位盲评专家，盲评专家读到 `input-1` 的内容，调用 `research_query` 被拒绝；
- 盲评专家的请求里没有工作目录、`AGENTS.md`、项目目标和发布编号。
